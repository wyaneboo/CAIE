Programming & Software Engineering for AI

This is the topic where "physics degree, no CS" bites hardest — and the one that most separates an employable engineer from a notebook hobbyist. Nobody will pay you a senior salary for knowing what an eigenvalue is; they will pay you for shipping code that other people can run, test, trust, and maintain. The good news: the core ideas are few, and none of them are as hard as quantum mechanics.

Learning outcomes

  • Apply vectorized NumPy operations and explain broadcasting rules; profile and optimize Python code.
  • Use generators, decorators, context managers, and type hints idiomatically.
  • Apply version-control workflows (branching, rebasing, Conventional Commits); write unit, integration, and property-based tests for ML code.

3.1 Python — what's actually happening under the hood

Python is the lingua franca of ML not because it's fast (it's ~100× slower than C for raw loops) but because it's a pleasant orchestration language: the heavy math runs in compiled C/CUDA libraries (NumPy, PyTorch), and Python just conducts. Three facts about its internals you must know:

  • Everything is an object on the heap. Even the integer 3 is a ~28-byte object with a type pointer and a reference count. Variables are names bound to objects, not boxes containing values — which is why b = a for a list gives you two names for one list (mutating via either is visible to both), and why default mutable arguments (def f(x, cache={})) are a famous bug: the dict is created once, at function definition, and shared across calls.
  • Memory is managed by reference counting (plus a cycle-detecting garbage collector). An object dies when its refcount hits zero. This is deterministic and simple — and it's the reason for fact three:
  • The GIL (Global Interpreter Lock) lets only one thread execute Python bytecode at a time, because refcount updates aren't thread-safe without it. Consequence: Python threads don't speed up CPU-bound Python code. They're fine for I/O-bound work (waiting on network/disk releases the GIL), and NumPy/PyTorch release the GIL inside big C kernels. For real CPU parallelism you use processes (multiprocessing), or you push the work into the compiled layer — which is what vectorization is.

Broadcasting is NumPy's rule for combining arrays of different shapes without copying: align shapes from the right; dimensions match if equal or if one of them is 1 (the size-1 dimension is virtually stretched). So shape (32, 1, 512) + (64, 512) → (32, 64, 512). It's how you write "subtract the mean of each row" without a loop, and misunderstanding it is the #1 source of silent shape bugs — an operation that should have errored instead broadcasts happily and produces garbage of a legal shape.

Profiling before optimizing is a professional reflex: cProfile tells you which function eats the time, line_profiler which line, memory_profiler/tracemalloc where the RAM goes. The empirical rule: 95% of runtime lives in 5% of the code, and your guess about which 5% is usually wrong.

3.2 Software engineering practice — the craft part

Version control. Git tracks snapshots of your project as a graph of commits. The professional workflow: never commit to main directly; cut a branch per change, open a pull request, get review, merge. Rebasing replays your branch's commits on top of the latest main — a linear, readable history — versus merging, which ties the histories together with a merge commit. Rule of thumb: rebase your own unpushed work; never rebase commits others have already built on (you'd be rewriting shared history). Conventional Commits standardizes messages (feat:, fix:, refactor:…) so changelogs and semantic versions can be generated automatically.

Testing ML code is genuinely harder than testing normal code, because the output is statistical. The layered strategy:

  • Unit tests pin down deterministic pieces: does the tokenizer round-trip? Does the loss decrease on one overfit batch? Does a shape-(3,4) input produce shape-(3,2) output?
  • Integration tests run the pipeline end-to-end on a tiny fixture dataset: data → features → train 2 steps → save → load → predict. Most production breakage lives in the seams these cover.
  • Property-based tests (the hypothesis library) generate hundreds of random inputs and assert invariants: "softmax outputs always sum to 1," "normalization is idempotent," "augmented images keep their labels." You state the physics; the framework hunts for counterexamples.

Reproducible environments. "Works on my machine" is a confession, not a defense. Three escalating tools: venv isolates one project's packages; Poetry (or uv) additionally locks the exact version of every transitive dependency in a lockfile, so a teammate installs bit-identical libraries; Docker freezes the entire operating system — Python itself, CUDA drivers, system libraries — into an image that runs the same on your laptop and on a cluster. ML adds one more layer the syllabus will revisit in Topic 13: reproducibility also requires pinning data, random seeds, and hardware nondeterminism, not just code.

Architecture. "Clean architecture" compressed to one sentence: dependencies point inward, from volatile details (databases, APIs, frameworks) toward stable business logic — never the reverse. The SOLID principles are five aging-but-useful heuristics for that; the two worth memorizing verbatim are Single Responsibility (one module, one reason to change) and Dependency Inversion (depend on interfaces, not concrete implementations — so you can swap "OpenAI API" for "local model" without rewriting the caller). In ML systems the classic sin is entangling data loading, feature computation, model definition, and serving in one notebook. Separate them, because they change at different speeds and are tested in different ways — Topic 13's train/serve skew is what happens when you don't.

3.3 Computational foundations — Big-O and the machine

Big-O answers one question: how does cost scale as input grows? Constants are dropped because they're hardware-dependent; growth class isn't. An \(O(n^2)\) attention over a 100× longer sequence costs 10,000× more — that single fact drives half of Topic 8's architecture research. The classes worth recognizing on sight: hash lookup \(O(1)\); binary search \(O(\log n)\); a scan \(O(n)\); sorting \(O(n \log n)\); pairwise comparisons \(O(n^2)\); naive matrix multiply of n×n matrices \(O(n^3)\); brute-force subsets \(O(2^n)\).

Reading exercise: at n = 200, n log n is ~1,500 while n² is 40,000 and 2ⁿ is ~10⁶⁰ — more operations than atoms in the galaxy. "It works on my 100-row test file" says nothing about the 10⁹-row production table; only the growth class does.

The memory hierarchy is the second half of performance literacy. Arithmetic is nearly free; moving data is what costs. A CPU register is reachable in ~0.3 ns; main memory in ~100 ns; an SSD in ~100 µs; another datacenter in ~1 ms. Caches exploit locality — if you touch memory sequentially (like iterating a contiguous NumPy array), the hardware streams it; if you jump randomly (like chasing Python object pointers), you pay the full latency per access. This is the second reason vectorized code wins, independent of interpreter overhead.

CPU vs GPU vs TPU. A CPU is a few (8–64) very smart cores optimized for latency: branch prediction, deep caches, out-of-order execution — great for irregular, sequential logic. A GPU is tens of thousands of simple arithmetic units optimized for throughput: they execute the same instruction on many data elements in lockstep (SIMD/SIMT), which is exactly the shape of matrix multiplication — the same multiply-accumulate on every element of a tile. A TPU goes further: it hard-wires matrix multiplication into a systolic array and deletes everything else. The ranking is not "GPU better than CPU"; it's "each architecture wins on workloads that match its shape." Deep learning is ~90% matmul by FLOPs, hence the GPU era. The catch — arithmetic intensity: a GPU only hits peak FLOPs if you feed it enough work per byte moved from memory; small batches and tiny kernels leave it idle, waiting on the very memory hierarchy you just clicked through. That idea returns with a vengeance in Topics 12 and 20.

Jargon decoder
GIL
Global Interpreter Lock — CPython mutex allowing one thread to run Python bytecode at a time. Threads for I/O, processes (or C kernels) for CPU work.
vectorization
Replacing per-element interpreted loops with single whole-array operations executed in compiled code (and, at the hardware level, SIMD instructions).
SIMD / SIMT
Single Instruction, Multiple Data/Threads — one instruction applied to many elements in lockstep. The GPU's execution model.
CI/CD
Continuous Integration / Continuous Delivery — every commit automatically triggers tests (CI) and, if green, deployment (CD). Detailed in Topic 13.
lockfile
Machine-generated file pinning exact versions of all transitive dependencies (poetry.lock, uv.lock), making installs reproducible.
refactoring
Restructuring code without changing behavior — safe only when tests exist to prove behavior didn't change.
technical debt
Future work you implicitly borrowed by shipping the quick version now. Interest compounds.
arithmetic intensity
FLOPs performed per byte moved from memory. Below the hardware's ratio (~100–300 for modern GPUs), you're memory-bound and FLOPs sit idle.

Self-check

1. Your feature-extraction script is CPU-bound pure Python. You split it across 8 threads and see no speedup. Why?

c. One thread holds the GIL at a time for CPU-bound Python. Threads would help if the time were spent in I/O waits or in GIL-releasing C kernels.

2. Arrays of shape (128, 1, 64) and (8, 64) are added. The result is:

b. Align right: (128,1,64) vs (·,8,64). 64=64 ✓; 1 vs 8 → stretch to 8; missing dim → 128. Legal, silent, and shape-(128,8,64) — which is also why broadcasting bugs are silent: verify intent with explicit reshape/einsum when in doubt.

3. Which test is the property-based one?

d. Property-based testing asserts invariants over generated inputs rather than specific examples. (a) is a unit test, (b) integration, (c) an evaluation gate.

4. A training step does very little math per byte loaded (low arithmetic intensity). The GPU utilization graph will show:

a. Below the hardware's FLOPs-to-bandwidth ratio, the kernel is memory-bound. Batching, operator fusion, and mixed precision (Topic 12) all raise intensity.
