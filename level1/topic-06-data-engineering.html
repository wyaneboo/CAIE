Data Engineering Fundamentals

Models are downstream of data, so seemingly small storage and timing decisions can dominate their reliability. This topic is small in exam weight but enormous in career weight: the engineer who cannot reason about where the data lives, how it moves, and why training and serving see different values can lose weeks to bugs that were never in the model.

Learning outcomes
  • Describe structured, semi-structured, and unstructured data formats (Parquet, Avro, JSON, ORC).
  • Explain ETL vs ELT and batch vs streaming paradigms.
  • Apply SQL: aggregation, joins, window functions, CTEs.
  • Describe warehouses, lakes, lakehouses; data validation, schema enforcement, quality monitoring; feature stores and training/serving consistency.

Orientation — follow one record from source to model

Data engineering is the design of a trustworthy path from an event in the world to a value a person, dashboard, or model can use. Imagine a card payment: an application emits an event, a transport carries it, storage keeps it, transformations validate and combine it, and a training or serving system reads the result. At every boundary ask four questions: what does one row mean, when did this fact become knowable, which version of the schema applies, and can the work be repeated safely?

TermPlain-language meaningWhy it matters

A pipeline is a chain of contracts, not a collection of tools

A useful mental model is source → transport → storage → transform → quality gate → consumer. Each arrow is an interface. Tools can change while the engineering questions remain: latency, throughput, cost, correctness, recoverability, security, and ownership. “Real time” is therefore not automatically better; it is one point in a design space.

Start with two declarations

Grain: what real-world unit does one output row represent? Knowledge boundary: what information was genuinely available at the time the output would have been produced? These two declarations help prevent many join bugs and temporal leakage.

6.1 How data is shaped and stored

Purpose — choose a representation that matches how data is read

Structured data follows an explicit tabular or relational schema. Semi-structured data has recognizable fields but permits variation between records, as JSON often does. Unstructured data—images, audio, free text, video—does not naturally fit a fixed table, although its metadata usually does. These are descriptions of logical organization, not permanent properties: JSON can be strictly validated, and text can be converted into structured features.

Worked classification

A payment table with fixed columns is structured. An API response whose optional nested fields vary is semi-structured. A receipt photograph is unstructured, while its capture time, merchant, and storage URI form a structured metadata row. Real systems commonly carry all three together.

A format does not guarantee performance on its own. File size, compression codec, row-group statistics, partition design, engine support, and the query all matter. Use text formats at boundaries where inspectability and interoperability dominate; use typed binary formats when repeated scale makes parsing and scanning material.

Row versus column layout — count the bytes the query must touch

Storage and memory reward contiguous reads. A transactional lookup commonly needs most fields of one record, so keeping a row together is useful. An analytical query commonly needs a few fields from many records, so keeping each column together enables projection: reading only the requested columns. A simplified columnar scan estimate is \(B_{scan}=N\,W_{selected}\,f_{partition}\,f_{groups}\,r_{compression}\). Metadata, indexes, caching, and engine overhead are omitted, so treat it as a comparison model, not a bill forecast.

The factors are deliberately editable. A real engine may use indexes, caches, metadata reads, different compression by column, or additional filtering. The honest claim is directional: column projection can remove unneeded bytes; it does not promise a fixed speed-up.

Inside a columnar file — row groups make pruning possible

Parquet divides rows horizontally into row groups. Within each group, values from one column form a column chunk, which is divided into pages. Encodings such as dictionaries and run-length encoding exploit repeated values; a compression codec then reduces the encoded bytes. A Parquet file footer records its schema and structural metadata; the schema is not repeated inside every record. File and page metadata can store statistics such as minimum, maximum, and null count. If a filter asks for event_date = '2026-08-18' and a row group's range cannot match, the engine can skip that group. This is often called predicate or filter pushdown, though exact pruning support depends on the format, writer, engine, and expression.

Worked scan estimate

One million rows have widths 8, 24, 12, 8, and 8 bytes: 60 MB logical. A query selects columns 3 and 4, keeps 25% of date partitions and 50% of row groups, and the physical-to-logical ratio is 0.4. The simplified columnar estimate is \(10^6(12+8)(0.25)(0.50)(0.40)=1.0\) MB. The result assumes the selected partitions and groups contain that fraction of rows and ignores metadata and minimum I/O units.

Partitioning and the small-file problem

Dataset partitions are usually directory or table subdivisions that a catalog can prune before opening files. Choose keys that appear in common filters and produce reasonably balanced groups; date is often useful, while a unique customer identifier often creates far too many partitions. Over-partitioning and frequent tiny writes create the small-file problem: listing, opening, scheduling, and metadata work can dominate the useful scan. Periodic compaction combines small files, but it consumes compute and must preserve transactional correctness. 

WRITE_BATCH(batch):
  validate batch against the declared schema
  derive a bounded partition key, such as event_date
  write to a temporary or transactionally isolated location
  publish metadata only after all files are durable

COMPACT(partition):
  read the current snapshot of many small files
  write fewer target-sized files with useful row-group statistics
  atomically replace the snapshot; retain old files until safe cleanup
Failure mode — partition by every filterable field

High-cardinality or badly skewed keys produce empty directories, tiny files, and hotspots. Partition coarsely, then rely on clustering, sorting, row-group statistics, or indexes for finer skipping where the chosen engine supports them.

Topic 3's memory hierarchy explains the layout choice: sequential useful bytes amortize storage and network latency. Columnar layout improves locality for a projected analytical scan; row layout improves locality for reconstructing a complete record. Neither is universally faster.

6.2 Moving data — ETL, ELT, batch, streaming

Purpose — move facts without losing their meaning or recoverability

Every pipeline extracts from a source, transforms values or shape, and loads a destination. ETL performs important transforms before loading the target system. ELT first lands source-shaped data in the target platform, then transforms it there. This is a question of transform placement, not a guarantee of privacy, cleanliness, or governance. Both patterns require access control, validation, lineage, and a recoverable source or landing zone.

PatternUseful whenWatch for
ETLthe target cannot accept source shape; sensitive fields must be removed before that boundary; specialized transforms run elsewherean early transform can discard evidence needed for reprocessing; compute and orchestration live outside the target
ELTthe analytical platform can transform efficiently and governed raw history is valuablelanding raw data expands the security boundary; uncontrolled copies and rising warehouse cost
 
PIPELINE(run_interval):
  source_snapshot = extract(run_interval, reproducible_cursor)
  assert source_snapshot matches the producer contract
  land immutable input with run_id and code_version
  transform from declared inputs only
  validate output grain, keys, ranges, freshness, and volume
  publish output atomically; record lineage and quality results

This pattern supports replay because it records the input boundary, code version, and publication decision. “Immutable” here means append or version rather than overwrite without a trace; retention policy still applies.

Batch, micro-batch, and streaming — choose from a latency requirement

A batch job processes a bounded dataset on demand or a schedule. A micro-batch engine repeatedly processes small bounded intervals. A streaming engine treats input as unbounded and maintains state while events arrive; an implementation may still execute internally in micro-batches. The product's tolerated data age—not fashion—should set the architecture.

ModeTypical strengthEngineering burdenGood starting question
batchsimple replay, high throughput, complete bounded inputsfreshness limited by schedule and durationWould an hourly or daily answer change the decision?
micro-batchseconds-to-minutes freshness with bounded execution unitsoverlapping runs, checkpointing, small outputsCan the product tolerate interval-sized delay?
streamingcontinuous low-latency state updatesordering, late data, state growth, recovery, sink semanticsWhat measurable harm occurs if the answer is five minutes old?
Worked choice

A monthly risk report gains little from streaming; a replayable daily batch is easier to audit. A card authorization may need features in tens of milliseconds, so an event stream and online state can be justified. The same company can—and usually should—use different modes for different latency contracts.

If events arrive at 120 per second, a processor handles 100 per second, and the mismatch lasts 300 seconds, the backlog grows by \(\max(0,120-100)\times300=6{,}000\) events. This assumes constant rates and no parallel capacity; after input slows, spare capacity must drain the queue.

Time in a stream — event, arrival, processing, and availability

Event time is when the real-world action occurred. Arrival or ingestion time is when the platform received it. Processing time is when a worker handled it. Availability time is when a value became usable by a particular consumer after upstream delay and publication. Networks, offline devices, and retries make these clocks differ.

A time window such as [90, 100) groups events by event time. The engine cannot wait forever for delayed records, so it advances a watermark: a statement that it does not expect much more data earlier than some event time. In this chapter's simplified policy, \(W=t_{\mathrm{max\ observed}}-L\), where \(L\) is allowed lateness. It is a heuristic progress boundary, not proof that no earlier event can arrive.

Worked clock example

If the maximum observed event time is 12:10 and allowed lateness is five minutes, the simplified watermark is 12:05. An event stamped 12:03 that arrives afterward is late relative to that watermark; whether it is dropped, counted separately, or used to revise output is a policy choice.

A late-data policy can (1) drop and count the record, (2) send it to a side output for repair, or (3) update/retract a previously emitted result if downstream consumers can accept revisions. A watermark without an explicit policy merely hides the decision.

Delivery semantics, idempotency, and replay

At-most-once processing may lose work but avoids redelivery. At-least-once retries after uncertainty, so duplicates are possible. Exactly-once must be interpreted with a stated scope: some engines guarantee one state transition inside their managed boundary, but an end-to-end exactly-once effect additionally needs replayable sources and transactional or idempotent sinks. A message broker alone cannot guarantee the final external side effect. 

HANDLE(event):
  require stable event.id
  begin sink transaction
  if processed_ids contains event.id:
      commit without repeating the effect
      return
  upsert output using deterministic key and event version
  record event.id as processed in the same transaction
  commit

REPLAY(from_checkpoint):
  read the immutable log from the recorded offset
  run the versioned transform deterministically where practical
  write through the same idempotent publication path
Failure modes

An idempotency key that changes on retry does not deduplicate. Recording “processed” separately from the business write creates a crash gap. External emails, payments, or APIs may need their own idempotency contract. Non-deterministic transforms must persist the randomness, model version, or resolved output needed for reproducible replay.

Warehouse, lake, and lakehouse — overlapping capability bundles

A warehouse usually presents managed tables, SQL optimization, governance, and transactional behavior. A lake usually stores open files in object storage and separates storage from many possible compute engines. A lakehouse adds table metadata and protocols—commonly transactions, snapshots, schema controls, and time travel—over lake files. Modern products overlap, so these labels describe capability bundles rather than strict physical laws.

NeedOften favorsQuestions that decide
governed BI with predictable SQL experiencemanaged warehouseconcurrency, workload isolation, security model, data sharing, cost controls
open-format storage for varied engines and large raw assetslakecatalog ownership, file hygiene, transaction needs, retention, governance enforcement
open files plus table-level snapshots and updateslakehouse table formatengine support, concurrency protocol, compaction, metadata scaling, operational maturity

When to use what: begin with workload and organizational constraints, not the category name. A small team may benefit more from one managed platform than from operating a broad hybrid. A regulated multi-engine estate may value open formats and explicit control enough to accept the extra operations.

6.3 SQL — the one language every AI engineer actually uses daily

Purpose — declare the result while protecting its grain

SQL is declarative: state the result and let the optimizer choose a physical plan. Before writing a clause, declare the grain: what one input row and one output row represent. A table at one row per order cannot be joined casually to a table at one row per order item; the latter multiplies each order. Keys and cardinalities are part of correctness, not merely performance.

Grain card

Question: total paid amount per customer per calendar month.
Source grain: one row per payment attempt.
Filter: successful attempts only.
Output grain: one row per customer-month.
Uniqueness expectation: (customer_id, month) is unique.

A fuller simplified logical order is FROM/JOIN → WHERE → GROUP BY → aggregate → HAVING → window expressions → QUALIFY → SELECT → DISTINCT → ORDER BY → LIMIT. QUALIFY is dialect-specific; without it, filter window results in an outer query. Alias visibility also varies by dialect, so do not assume a SELECT alias is legal in earlier clauses. Optimizers may rewrite physical execution while preserving allowed semantics. The logical model still explains why WHERE filters rows before aggregates exist and HAVING filters groups after aggregation.

NULL, ordering, and aggregation — three sources of plausible wrong answers

NULL means missing or unknown, not zero or an empty string. Comparisons with NULL produce unknown, the third value in SQL's three-valued logic; a WHERE clause keeps only true. Use IS NULL, not = NULL. COUNT(*) counts rows, while COUNT(column) counts non-NULL values. Aggregates such as SUM usually ignore NULL inputs, but an all-NULL group can still produce NULL depending on the function.

ExpressionOn values 10, NULL, 30Interpretation
COUNT(*)3three input rows
COUNT(amount)2two known amounts
AVG(amount)20mean of known values, not 40 ÷ 3
amount = NULLunknown for every rowdoes not find missing values

A table has no promised presentation order unless the final query specifies ORDER BY. LIMIT 100 without an ordering rule can return a different valid subset as files, plans, or parallelism change. For deterministic ties, add a stable secondary key.

Joins — calculate multiplicity before trusting the result



  For an inner equality join, if key \(k\) occurs \(L_k\) times on the left and \(R_k\) times on
  the right, that key contributes \(L_kR_k\) rows. Total output is

  ordinary equality join, NULL does not equal NULL, so declare how missing keys should be handled.

Window functions and CTEs — preserve rows while adding context



  A window function calculates over related rows without collapsing them. The
  PARTITION BY clause resets the calculation by entity; the window's
  ORDER BY defines sequence; the frame defines which neighboring rows participate.
  For a row-by-row cumulative value, state
  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. In some dialects, an ordered window's
  default is a RANGE-style frame that includes peers sharing the same order value, so
  duplicate timestamps can change the result. Use a deterministic tie-breaker where order matters.



SELECT
  customer_id,
  event_time,
  amount,
  SUM(amount) OVER (
    PARTITION BY customer_id
    ORDER BY event_time, event_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS spend_so_far
FROM valid_payments;



  A CTE names a subquery with WITH, which helps expose stages and test
  their grains. It is not inherently a performance optimization: an engine may inline, materialize,
  or otherwise rewrite it. Inspect the query plan and engine documentation when reuse or cost matters.




Point-in-time joins — reproduce what was knowable then



  A training example at prediction time \(t_p\) may use only a feature whose event time and
  availability time satisfy \(t_e\le t_p\) and \(t_a\le t_p\). Among eligible versions, an as-of
  join usually selects the latest relevant event per entity. If one event has multiple eligible
  corrections, select by eligible availability time and a deterministic version key. Tracking availability prevents a late
  backfill from appearing in historical training rows as though it had been known earlier.

6.4 Quality, schemas, and the feature store


Data contracts and schema evolution — compatibility includes meaning



  A data contract records the producer-consumer agreement: ownership, grain, keys,
  names, physical types, units, allowed values, null meaning, event and availability timestamps,
  freshness, and change policy. A file schema captures only part of that agreement. Changing
  distance from kilometres to metres while keeping a floating-point type is a breaking
  semantic change even though a schema checker sees no difference.






  
ChangeOften compatible when…Safer migration

  
  
add an optional fieldold readers ignore unknown fields and new readers define missing behaviorpublish it as nullable or with a documented default; test representative readers

  
widen a numeric typethe format and every reader support the conversion without lossdual-read or dual-write during a versioned transition

  
rename or remove a fieldrarely transparent to existing named-field consumersadd the replacement, migrate consumers, observe usage, then deprecate

  “Backward” and “forward” compatibility depend on which writer and reader versions must coexist,
  and the exact rules differ across Avro, Parquet readers, APIs, and databases. Test compatibility
  with real consumers. Rejecting incompatible writes can protect curated tables, while quarantining
  the input preserves evidence for repair; blindly coercing values can destroy meaning.




Quality is multi-dimensional — monitor, quarantine, repair, replay



  Validation is testing applied to data, but one score cannot summarize it. Common dimensions are
  validity (values satisfy rules), completeness (required values are
  present), uniqueness (declared keys do not repeat), consistency
  (related representations agree), timeliness (data arrive within the freshness
  contract), and volume/distribution (unexpected shifts are investigated).
  Distribution alerts indicate change; they do not by themselves prove corruption.




  
Worked quality gate

  
A daily partition has 10,000 rows and 120 missing required merchant categories, so completeness
  is \((10000-120)/10000=98.8\%\). The contract requires at least 99.5%, zero duplicate payment IDs,
  and publication within 30 minutes; this batch also has three duplicate IDs and is 90 minutes late.
  The safe outcome is to withhold this version from consumers, keep the raw batch, alert its owner,
  repair the cause, then replay. Silently dropping offending rows would change the population.




QUALITY_GATE(candidate):
  schema_results = validate names, types, nullability, and versions
  content_results = validate keys, ranges, relationships, and known invariants
  operational_results = validate volume, freshness, and distribution alerts
  persist every result with dataset version and run_id
  if any blocking contract fails:
      quarantine candidate; preserve source; notify owner
  else:
      publish candidate atomically

REPAIR_AND_REPLAY(quarantined_run):
  correct source data or versioned transform; do not edit evidence silently
  replay from the recorded source boundary
  pass the same gate; publish a new version; document lineage



  
Failure modes

  
Thresholds that never evolve become noise. Automatic repair without provenance can mask upstream
  defects. Blocking every mild distribution shift can destroy availability. Classify checks as
  blocking, warning, or informational, assign ownership, and rehearse replay before an incident.





Feature stores — reduce training/serving skew across two time scales



  Training/serving skew occurs when a model's production inputs differ from the
  feature definitions or time semantics used to build training data. Causes include duplicated
  transformation code, different NULL defaults, timezone or rounding rules, stale online values,
  late events, incompatible encodings, and leakage in offline joins.




  A feature-store architecture commonly includes a registry of definitions and metadata, an
  offline store for historical feature versions, an online store for low-latency current values,
  materialization that moves computed values online, and point-in-time retrieval for training.
  Centralizing these paths can reduce skew and improve reuse; it does not make two systems
  byte-identical or make inconsistency impossible. Teams must still test semantic parity, freshness,
  entity keys, and event/availability timestamps.

TTL, backfills, and when a feature store is unnecessary



  A feature's time to live (TTL) defines how long an online value may be treated as
  usable. If \(t_{serve}-t_{feature}>TTL\), serving must follow a declared policy: refresh, use a
  documented fallback, mark missing, abstain, or degrade the product. A longer TTL improves
  availability but risks stale decisions; a shorter TTL raises compute and missing-value pressure.



BACKFILL(feature_version, interval):
  pin source snapshots and transformation version
  compute versions with event_time and available_time
  run quality and point-in-time leakage checks
  publish as a new offline version; do not rewrite audited history in place
  materialize online only if that version is approved for serving
  compare offline fixtures with online retrieval before rollout

3. The largest observed event time is 12:10 and allowed lateness is five minutes. Under this chapter's simplified rule, what is the watermark?

  

    
    
    
    
  

  
b. \(12{:}10-5\text{ minutes}=12{:}05\). The watermark is a progress estimate. The declared late-data policy still decides what happens to an earlier arrival.





  
4. Which statement correctly distinguishes a window function from a CTE?

  

    
    
    
    
  

  
d. Window functions retain the input row grain while adding values such as running totals; explicit frames and deterministic ordering matter. A CTE exposes a logical query stage, but the optimizer may inline or materialize it.





  
5. A team wants governed SQL tables but also open object-store files usable by several engines, with snapshot history and transactional table updates. Which bundle most closely fits?

  

    
    
    
    
  

  
a. Lakehouse table formats add metadata, snapshots, and transaction protocols over lake files. Product categories overlap, so compatibility and operations still need evaluation.





  
6. A query must keep only regions whose total sales exceed 400. Which clause belongs after grouping?

  

    
    
    
    
  

  
b. WHERE filters input rows before aggregates exist; HAVING filters the groups after GROUP BY has formed them and aggregate values can be evaluated.





  
7. Key A appears twice on the left and three times on the right; key B appears once on the left and twice on the right. How many rows does their inner equality join produce?

  

    
    
    
    
  

  
d. A contributes \(2\times3=6\); B contributes \(1\times2=2\); total 8. This multiplication is why a many-to-many join can inflate aggregates.





  
8. A feature event occurred at 09:55 but its corrected value became available at 10:05. May a training row for a 10:00 prediction use that corrected value?

  

    
    
    
    
  

  
b. The value was not knowable at 10:00. A correct as-of join enforces both event-time and availability-time boundaries.





  
9. A producer changes distance from kilometres to metres without changing its type, and the next batch also fails the completeness contract. What is the safest response?

  

    
    
    
    
  

  
a. Compatibility includes units and meaning, while a quality gate protects consumers. Quarantine plus versioned repair and replay preserves evidence and lineage.





  
10. When is a feature store least likely to justify its additional platform cost?

  

    
    
    
    
  

  
c. Tested, versioned SQL may fully solve that case. A feature store is valuable when reuse, online latency, skew control, or temporal retrieval offsets its operational burden.
