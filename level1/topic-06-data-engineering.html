Data Engineering Fundamentals

Models are downstream of data, and in industry the data work is 60–80% of the job. This topic is small in exam weight but enormous in career weight: the engineer who can't reason about where the data lives, how it moves, and why training and serving see different values will lose weeks to bugs that were never in the model.

Learning outcomes
  • Describe structured, semi-structured, and unstructured data formats (Parquet, Avro, JSON, ORC).
  • Explain ETL vs ELT and batch vs streaming paradigms.
  • Apply SQL: aggregation, joins, window functions, CTEs.
  • Describe warehouses, lakes, lakehouses; data validation, schema enforcement, quality monitoring; feature stores and training/serving consistency.

6.1 How data is shaped and stored

Structured data has a fixed schema (database tables). Semi-structured carries its schema with each record (JSON, XML) — flexible, verbose, slow to scan. Unstructured is everything else: text, images, audio — the raw feedstock of deep learning. The formats you must be able to compare:

FormatLayoutBest atNotes
JSON / CSVrow, textinterchange, debugging by eyeno types (CSV), no compression, parse cost per read; fine for small, terrible for big
Avrorow, binarystreaming pipelines, Kafka messagesschema travels with data; good for write-heavy, record-at-a-time
Parquetcolumnar, binaryanalytics & ML training readsreads only needed columns; heavy compression per column; the default for data science
ORCcolumnar, binaryHive/warehouse workloadsParquet's sibling from the Hadoop lineage; indexes and stats built in

The row-vs-column decision is a physics-of-data question: disks and memory reward sequential access (Topic 3's hierarchy). Analytics queries touch few columns of many rows; columnar layout makes those bytes contiguous. Transactional lookups touch all columns of one row; row layout wins there.

Same 1M-row table (5 columns), two physical layouts. Pick a query and see which blocks each layout must read.

Columnar wins the analytics queries by ~5× here (and by 50–100× in practice, because each column also compresses far better when stored together). The point lookup is the row store's home game — which is why OLTP databases (Postgres) are row-oriented and OLAP warehouses (BigQuery, Snowflake) are columnar. One layout cannot win both.

6.2 Moving data — ETL, ELT, batch, streaming

ETL (extract → transform → load): clean and reshape before loading into the destination — the classic pattern when warehouse compute was scarce. ELT: land raw data first, transform inside the warehouse with SQL (dbt is the emblematic tool) — today's default, because storage is cheap, warehouse compute is elastic, and keeping the raw data means you can re-derive anything when (not if) the transform logic changes.

Batch processes accumulated data on a schedule (hourly/daily) — simple, reprocessable, high-latency. Streaming processes events seconds after they occur (Kafka for transport, Flink/Spark Streaming for compute) — low-latency, but you inherit hard problems: out-of-order events, exactly-once semantics, windowing. The professional rule: batch unless the product genuinely needs freshness (fraud scoring, live recommendations), because streaming's operational cost is 3–10× batch. Many real systems run a hybrid (a streaming path for the last hour, batch for history).

Where it all lives. A data warehouse stores curated, schema-enforced tables optimized for SQL analytics. A data lake is cheap object storage (S3/GCS) holding files of anything — flexible, and one governance lapse away from a "data swamp." The lakehouse (Delta Lake, Iceberg, Hudi) adds warehouse discipline — ACID transactions, schema enforcement, time travel — as a metadata layer over lake files, and is where the industry has converged for ML workloads.

6.3 SQL — the one language every AI engineer actually uses daily

SQL is declarative: you state what you want; the engine plans how. The mental model that unlocks everything is the logical evaluation order — which is not the order you write: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. That's why you can't use a SELECT alias inside WHERE, and why HAVING exists at all (it filters after aggregation, WHERE filters before).

6.4 Quality, schemas, and the feature store



  Data validation is testing (Topic 3) applied to data: assert schemas (column
  names, types, nullability), ranges (age ∈ [0, 130]), distributions (today's mean within k·σ of
  history), freshness, and volume. Tools: Great Expectations, dbt tests, Pandera. Schema
  enforcement at write time beats detection at read time: a pipeline that rejects a
  malformed batch loudly is a gift; one that silently coerces strings to NaN is a time bomb —
  and Topic 13's drift monitoring is this idea extended into production.




  A feature store solves one specific, expensive problem:
  training/serving skew. The features you compute offline for training (in SQL,
  over the warehouse) must be byte-identical in logic to the features computed online at
  inference time (in a microservice, in milliseconds). Write the logic twice and the two copies
  drift; the model then sees inputs from a distribution it never trained on, and quietly degrades.
  A feature store (Feast, Tecton) defines each feature once, serves it from an offline
  store for training and an online low-latency store for inference, and — critically — supports
  point-in-time-correct joins: when building training data for a prediction made on March 3,
  it serves feature values as they were on March 3, not as they are today. Skipping that is
  time-travel leakage (Topic 4's sin, at infrastructure scale).





  
Jargon decoder

  

    
OLTP / OLAP
Transaction processing (many small reads/writes, row stores) vs analytical processing (big scans, columnar stores).

    
ACID
Atomicity, Consistency, Isolation, Durability — the transactional guarantees warehouses/lakehouses give and raw file dumps don't.

    
schema-on-write / schema-on-read
Enforce structure when storing (warehouse) vs when querying (lake).

    
dbt
The standard tool for ELT transforms: SQL models with dependencies, tests, and docs, version-controlled like code.

    
Kafka
The dominant event log / message bus for streaming: producers append events, consumers read at their own pace.

    
partitioning
Splitting stored data by a key (usually date) so queries scan only relevant chunks — the #1 lever for query cost.

    
data lineage
The recorded ancestry of a dataset: which sources and transforms produced it. What you consult when a number looks wrong.

    
point-in-time join
Joining features to training labels using only information available at the label's timestamp — the anti-leakage join.
