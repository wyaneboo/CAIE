MLOps & Production Engineering

A production model is one versioned component in a changing service. It consumes live data, shares a latency and reliability budget with dependencies, influences future data, and is judged long after deployment when outcomes arrive. MLOps makes that system reproducible, observable, safely changeable, and recoverable. This chapter teaches the reasoning chain behind each control, not a vendor-specific checklist.

Learning outcomes
  • Describe the end-to-end ML lifecycle and diagnose train/serve skew.
  • Design CI/CD pipelines for models, including tests, validation gates, and automated retraining.
  • Explain model registries, versioning, and lineage tracking.
  • Compare batch, real-time, and streaming serving and reason about latency versus throughput.
  • Describe inference optimization: quantization, pruning, distillation, and compilation with ONNX/TensorRT nuance.
  • Explain data drift, concept drift, performance degradation, label lag, and alerting.
  • Compare shadow, canary, and A/B deployments.
  • Diagnose production incidents from latency, error, saturation, data, and model signals.
Vocabulary before the lifecycle
Artifact
A versioned output such as a model file, tokenizer, feature definition, calibration map, threshold, or compiled engine.
Build, release, deploy
Create an artifact; approve a version for use; place that version in an environment. These are separate events.
CI, CD, and CT
Continuous integration tests changes; continuous delivery/deployment promotes approved artifacts; continuous training produces new model candidates.
Registry and lineage
A catalog of versioned model metadata, and the trace from a deployed prediction back through artifacts, code, data, and configuration.
SLI, SLO, and SLA
A measured service indicator, an internal target for it, and an external agreement that may attach consequences.
Drift and degradation
A distribution changes; an outcome metric worsens. Either can occur without the other.
Rollback
Restore a known compatible release and its dependencies—not merely copy an older weight file.
The production reasoning loop

Specify the decision and SLOs → version data, code, features, and artifacts → test a candidate → release progressively → observe system, data, prediction, and outcome signals → contain and learn from failures → retrain only when evidence supports it. Every arrow needs an owner, evidence, and a recovery path.

13.1 The lifecycle, CI/CD, and the registry

Purpose — control a feedback loop, not a one-time model build

The lifecycle is cyclic: collect and validate data, construct point-in-time features, train, evaluate, package, release, serve, monitor, join delayed outcomes, and decide whether to update. A deployed model can change which users see an offer, which labels are later observed, and what data the next model receives. Monitoring and retraining therefore sit inside a feedback system, not after an independent prediction function.

Reproducibility asks, “Can we rebuild this candidate?” Operational traceability asks, “Which exact release produced this prediction?” Governance asks, “Who approved it against which evidence?” A mature lifecycle answers all three.

Train/serve skew — compare meanings at the same entity and timestamp

Train/serve skew means that the feature or preprocessing semantics used to learn differ from those used to predict. It includes code duplication, units, missing-value policies, category vocabularies, tokenizer versions, aggregation windows, feature freshness, and point-in-time leakage. A shared library or feature store reduces risk but does not prove identical timestamps, data availability, or rollout configuration.

Worked skew failure — dollars versus cents

Training records cart_value in dollars and learns coefficient \(0.02\). A typical value 50 contributes \(0.02\times50=1\) to the logit. Serving sends 5,000 cents, contributing \(100\), so probabilities saturate even though schema type and null checks pass. A semantic contract with unit metadata and a replay test on identical entity-time examples catches what a generic “number” schema cannot.

Automated retraining — automate candidate production, not blind promotion

Continuous training may be scheduled, event-triggered, or requested after diagnosis. A drift alert is evidence to investigate, not proof that a new model will help. The pipeline should freeze the eligible data window, validate labels and sampling, reproduce a baseline, train a candidate, and send it through the same gates and progressive delivery as any human-triggered build.

Guard against feedback and label leakage: the incumbent may determine who receives treatment and therefore whose outcome is observed. Retraining on that selected log can reinforce policy bias. Define minimum label completeness, delay/censoring rules, trigger cooldowns, and a champion– challenger record. If labels are insufficient, wait or use a separately justified proxy; do not silently redefine success.

Registry, versioning, and lineage — make release and rollback compatible

A registry stores model-version metadata and lifecycle state; an artifact store holds bytes. Implementations may combine them, but the concepts differ. A useful manifest links immutable digests for data, code, environment, feature definitions, weights, tokenizer, calibration, threshold, compiled engine, evaluation report, approver, and deployment.

Rollback is fast only when interfaces and state remain compatible. A previous model may require an old tokenizer, feature schema, or database interpretation. Rehearse rollback and roll-forward, preserve old dependencies for the retention window, and record migrations that are not reversible.

13.2 Serving — patterns and the latency–throughput tradeoff

Choose the serving pattern from freshness, deadline, and coupling

PatternRequest and resultStrengthCharacteristic risk
BatchScore a bounded dataset on a schedule; store outputsHigh utilization, simple retries, reproducible snapshotsPredictions can be stale; jobs may miss their completion deadline.
Online / real-timeServe a request synchronously within a deadlineUses the newest request contextTail latency, dependency failures, overload, cold starts.
StreamingConsume events continuously and emit/update predictions asynchronouslyFresh event-driven state without request couplingLate/out-of-order events, duplicate delivery, state and replay semantics.

“Streaming” does not guarantee exactly-once business effects or lower latency than every online service. “Batch” need not mean once nightly. Choose from the decision deadline, acceptable staleness, input availability, state requirements, cost, and recovery semantics. Hybrid systems often precompute expensive candidates in batch and rerank them online.

Latency, throughput, and queues — state the model before using the formula

Arrival rate is \(\lambda\), sustainable service capacity is \(\mu\), and utilization is \(\rho=\lambda/\mu\). Stability requires long-run \(\lambda<\mu\). Little's law, \(L=\lambda W\), relates average items \(L\), arrival rate, and average time \(W\) for a stable system under consistent boundaries.

The familiar divergence depends on a queue model. For an M/M/1 queue, \(W=1/(\mu-\lambda)\) and mean queue wait is \(W_q=\rho/(\mu-\lambda)\). Real inference has batching, multiple servers, heavy-tailed input lengths, priorities, and correlated bursts, so measure p50/p95/p99 rather than transferring that formula uncritically.

Worked capacity calculation

Suppose a full batch of \(B=8\) takes \(6+1.2B=15.6\) ms. Ideal saturated capacity is \(1000B/15.6=512.8\) requests/s. At 400 requests/s, offered utilization against that ideal is \(0.78\). This does not predict p99: low load may not fill batches, requests wait up to the batch window, long inputs vary service time, and retries can add load.

Dynamic batching — trade bounded waiting for denser execution

A batcher starts work when it reaches a size limit or a wait/deadline limit. Larger batches may amortize launch, scheduling, and memory-transfer overhead, but can raise latency, padding work, activation/KV memory, and head-of-line blocking. Bucket compatible shapes or lengths, propagate deadlines, and prevent a long request from delaying every short one.

Capacity planning should use the input-shape distribution and a tail-latency SLO at expected peak traffic with headroom. A server that achieves maximum throughput in a saturated benchmark may be unsuitable for an interactive deadline.

⚛ Physics bridge

Queue growth near capacity resembles critical slowing down, but the equation is model-specific. Utilization is a control parameter; tail latency reveals fluctuations and heavy tails that a mean hides. Measure the actual system rather than treating \(\rho/(1-\rho)\) as a universal law.

13.3 Making inference cheap — quantization, pruning, distillation, compilation

Start with the objective — optimize an end-to-end measured path

Decide whether the constraint is artifact size, device memory, energy, batch throughput, cold start, p99 latency, or cost per successful decision. Profile preprocessing, tokenization, feature lookup, host-to-device transfer, model kernels, postprocessing, and queueing. Optimizing model FLOPs cannot remove a remote feature-service bottleneck.

Preserve a reference package and evaluation set. Each transformation must pass numerical parity within a justified tolerance, task and slice metrics, calibration/threshold checks, supported shapes, load tests, and failure tests on the actual runtime and hardware.

Quantization — map real values to integers with explicit scales

Linear quantization represents approximately $$ x \approx s(q-z), $$ with integer \(q\), positive scale \(s\), and zero-point \(z\). Choices include weight-only or weight-and-activation, static or dynamic activation scales, symmetric or asymmetric mapping, and tensor/channel/group granularity. Smaller groups often track outliers better but add metadata and may change kernel support.

Post-training quantization (PTQ) converts a trained model; static activation PTQ needs representative calibration data. Quantization-aware training (QAT) simulates quantize/dequantize effects during training or fine-tuning. Neither guarantees speed: unsupported operators, dequantization/cast overhead, packing, small batches, or hardware without suitable integer kernels can erase or reverse the gain.

Worked weight-memory calculation

Seven billion FP16 weights occupy 14.0 GB. INT4 payload is 3.5 GB, but with one two-byte scale per 64 weights, metadata adds \(7\text{B}/64\times2=0.21875\) GB. Total 3.71875 GB gives \(14/3.71875\approx3.76\times\) compression—not exactly \(4\times\). Alignment, zero-points, sparse indices, tied weights, and runtime buffers can change the deployed total.

Pruning — distinguish zeros, storage sparsity, and executable speedup

Unstructured pruning sets individual weights to zero. It may reduce compressible storage, but a dense tensor and dense kernel still execute the same shape. Sparse formats need indices and a supported sparsity pattern; their overhead can dominate small or irregular tensors. Structured pruning removes channels, neurons, heads, blocks, or layers, changing dense shapes that ordinary kernels can exploit, but it may damage quality more per removed parameter.

Measure layer sensitivity, prune gradually, fine-tune, and export the actual smaller or sparse representation. “90% sparsity” is not “10× lower latency.” Report payload size, encoded size, realized kernel speed, end-to-end p99, and accuracy separately.

Distillation — train a smaller student from labels and teacher behavior

With teacher and student temperature-\(T\) distributions \(p_t^T,p_s^T\), one common objective is $$ L=\alpha\,\mathrm{CE}(y,p_s)+(1-\alpha)T^2 D_{\mathrm{KL}}\!\left(p_t^T\Vert p_s^T\right). $$ Temperature softens logits so relative probabilities expose similarities between classes. Distillation can also match hidden states or task-specific outputs. It requires a new training and evaluation job; the student can inherit teacher errors and may fail differently on rare slices. A smaller architecture is the source of deployability, not the word “distillation.”

Compilation, ONNX, and TensorRT — representation is not a speed guarantee

ONNX is a versioned intermediate representation and operator-set ecosystem for exchanging model graphs. A compatible runtime may perform graph rewrites and dispatch subgraphs to execution providers. Export can fail or change behavior because of unsupported/custom operators, operator version semantics, control flow, dynamic shapes, or preprocessing outside the graph.

TensorRT is NVIDIA's GPU inference optimizer/runtime. Its build phase selects tactics and produces a hardware/runtime-specific engine; dynamic dimensions require supported ranges and optimization profiles. Precision choices and different accumulation orders need accuracy checks, and engines have compatibility constraints. ONNX export and TensorRT compilation are steps in a measured deployment pipeline, not synonyms and not guarantees of unchanged predictions or fixed speedup.

Define each SLI's population, event time, processing time, aggregation window, release cohort, and minimum sample size. Track the model and feature versions with every prediction so an alert can be localized. Alerts need severity, owner, runbook, deduplication/cooldown, and an action; otherwise a dashboard becomes decoration.

Drift taxonomy — separate observable changes from causal claims

  • Data drift: \(P(X)\) changes. It is observable without outcome labels. Covariate shift is the narrower setting that additionally assumes \(P(Y\mid X)\) stays stable.
  • Concept drift: \(P(Y\mid X)\) changes. Stable inputs do not rule it out; labels or justified outcome proxies are needed.
  • Label/prior shift: \(P(Y)\) changes, sometimes with more specific conditional assumptions. It is not interchangeable with every concept shift.
  • Data-quality failure: a contract or pipeline breaks—units, nulls, joins, timestamps, stuck sensors. It can create apparent drift and should be repaired, not learned.
  • Performance degradation: an outcome metric worsens. Causes include drift, bugs, policy/threshold changes, serving errors, label-pipeline changes, and selection effects.

A detector identifies a statistical difference under its sampling assumptions; it does not name the cause or prescribe retraining. Compare seasonal/segment-matched baselines and investigate upstream changes before teaching the model to absorb a data bug.

Drift metrics — PSI is binned evidence, not a universal traffic light

For reference proportions \(p_i\) and current proportions \(q_i\) over identical bins, $$ \mathrm{PSI}=\sum_i(p_i-q_i)\ln\frac{p_i}{q_i} =D_{\mathrm{KL}}(p\Vert q)+D_{\mathrm{KL}}(q\Vert p). $$ This is the binned Jeffreys divergence. It is symmetric but not a metric; zero bins require a documented smoothing rule. The result depends on binning, sample size, segmentation, and the baseline. Conventional cutoffs such as 0.1 or 0.25 are domain heuristics, not significance levels.

Worked PSI calculation

Reference proportions \((0.4,0.3,0.2,0.1)\) and live proportions \((0.2,0.3,0.3,0.2)\) give \(0.2\ln2+0+(-0.1)\ln(2/3)+(-0.1)\ln(1/2)\approx0.2485\). That localizes contributions by bin but does not prove performance loss. Inspect counts, uncertainty, seasonality, feature semantics, and outcome metrics.

Alternatives include KS for one-dimensional continuous distributions, chi-square/category tests, Wasserstein distance, maximum mean discrepancy, and classifier two-sample tests. Multiple features and repeated windows create multiple-testing and alert-fatigue problems; monitor effect size and persistence as well as a p-value.

Label lag and performance — align prediction cohorts with mature outcomes

At day \(t\), labels may describe predictions made at \(t-\ell\), where \(\ell\) is the label delay. Plot metrics by prediction cohort and outcome maturity; otherwise a current model can be blamed for an old model's outcomes. Censoring matters: unresolved loans or patients are not negative outcomes, and only some decisions may ever receive a label.

During the blind window, use fast proxies—data contracts, score distributions, disagreement with a shadow reference, human-review samples—but name them as proxies. Also monitor label arrival rate, join success, class balance, and definition version: a broken label pipeline can look exactly like sudden performance collapse.

13.5 Progressive delivery — shadow, canary, A/B

The delivery ladder — each method answers a different question

MethodRouting and user effectBest evidenceImportant limitation
Shadow / dark launchMirror live inputs; incumbent response remains authoritativeCompatibility, latency, errors, disagreement, real-input distributionsNo causal user response; mirrored sensitive data, compute, and accidental side effects still create risk.
CanaryCandidate serves a bounded real cohortSafety, stability, latency, and quality guardrails under real interaction/loadA canary cohort may be too small or non-random for a business-effect conclusion.
A/B experimentRandomized units receive control or treatmentCausal effect on pre-specified outcomes under experimental assumptionsNeeds power, stable assignment, interference checks, time, and ethical/operational eligibility.

Teams may use one, two, or all three depending on risk and measurability. Shadow outputs must be prevented from calling side-effecting downstream systems. Canary rollback triggers should be predeclared and compared by release cohort. A/B assignment is usually by persistent user/entity, not request, to avoid cross-arm contamination.

A/B design — choose the effect and sample before watching the result

For two independent proportions \(p_0,p_1\), a common normal-approximation sample-size formula is $$ n\approx \frac{\left[ z_{1-\alpha/2}\sqrt{2\bar p(1-\bar p)} +z_{1-\beta}\sqrt{p_0(1-p_0)+p_1(1-p_1)} \right]^2}{(p_1-p_0)^2}, \qquad \bar p=\frac{p_0+p_1}{2}. $$ With baseline 10%, minimum detectable absolute lift 1 percentage point, two-sided \(\alpha=0.05\), and 80% power, this gives about 14,750 observations per arm. The approximation assumes independent units and fixed-horizon analysis.

Pre-register the primary metric, guardrails, randomization unit, eligibility, duration, analysis, and stopping rule. Check sample-ratio mismatch, novelty and day-of-week effects, missing outcomes, interference, multiple metrics, and repeated peeking. Statistical significance is not practical importance, and business uplift does not waive safety or fairness guardrails.

13.6 Incident triage — reading the dashboard

Triage workflow — contain harm, preserve evidence, then explain

  1. Declare and scope: user impact, affected release/region/slice, start time, severity, incident lead.
  2. Contain: stop rollout, shed load, disable unsafe automation, or roll back only when the path is known compatible.
  3. Build a timeline: deploys, data/schema changes, traffic, dependency events, and first signal movement.
  4. Compare cohorts: candidate versus incumbent, region, shape/length, feature version, and control traffic.
  5. Test hypotheses: seek a discriminating signal; do not change several variables at once.
  6. Recover and verify: watch user-impact SLIs, queues, labels, and delayed consequences—not only process health.
  7. Learn: blameless timeline, root and contributing causes, detection gap, owner and due date for corrective actions.

Preserve request IDs, release/feature/model versions, traces, sampled inputs under privacy rules, predictions, and rollback decisions. Do not “fix” an incident by deleting the evidence needed to understand it.

Self-check

1. Offline quality is strong, but the deployed model saturates its probabilities. Training used cart value in dollars while serving sends cents. What is the most precise diagnosis and control?

b. The numeric type is valid but its meaning changed by 100×. Unit metadata and parity replay target this failure; retraining on the same dollar convention does not.

2. A scheduled retraining job produces a candidate after a drift alert. What should happen next?

d. Continuous training automates candidate creation. It does not turn a drift detector into a diagnosis or waive independent promotion evidence.

3. Which registry record best supports reproducibility and rollback?

a. Weights alone do not define behavior. Rollback also needs compatible preprocessing, runtime, interfaces, and state.

4. A full batch of 8 takes \(6+1.2(8)=15.6\) ms. Which statement is correct?

c. \(1000\times8/15.6=512.8\). Capacity arithmetic is not a tail-latency model, and stable operation needs headroom.

5. Which inference-optimization claim is technically sound?

b. Payload arithmetic is only one layer. Metadata, representation, runtime kernels, supported shapes, and numerical effects require measurement.

6. Reference bins are \((0.4,0.3,0.2,0.1)\), live bins \((0.2,0.3,0.3,0.2)\). What is the best PSI interpretation?

c. Summing \((p_i-q_i)\ln(p_i/q_i)\) gives about 0.2485. It is binned distribution evidence, not a causal or performance conclusion.

7. Input distributions remain stable, but correctly joined mature labels show recall falling for new prediction cohorts. Which statement is strongest?

d. Input-only monitors cannot rule out concept drift. The premise says the label join was checked, removing one important alternative cause.

8. Which progressive-delivery statement is precise?

a. The methods answer different questions. Mirrored traffic still needs isolation and data governance; causal inference needs experimental discipline.

9. A 10% baseline and 1-percentage-point MDE need roughly 14,750 independent units per arm at 95% two-sided confidence and 80% power. What else is essential?

c. The calculator is a planning approximation. Valid experiments require design, instrumentation, and analysis assumptions beyond the arithmetic.

10. Reported AUC falls after a 30-day label lag, while input PSI is flat—but label completeness simultaneously drops from 96% to 41%. What is the best first action?

b. Outcome monitoring is only as trustworthy as label coverage and semantics. Repair and replay the label pipeline before diagnosing the model.
