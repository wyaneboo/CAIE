MLOps & Production Engineering

A model in a notebook is a claim; a model in production is a promise. This topic is about keeping that promise after the data shifts, the traffic spikes, and someone deploys a new tokenizer on a Friday. The famous finding of Google's "Hidden Technical Debt" paper: the ML code is a small black box in the middle of a sprawling system of pipelines, configuration, serving, and monitoring — and the system, not the model, is where careers are made and incidents happen. The exam tests this topic with vignettes: dashboards full of signals, and you diagnosing.

Learning outcomes
  • Describe the ML lifecycle and diagnose training–serving skew.
  • Design CI/CD for models: tests, validation gates, registries, lineage, automated retraining.
  • Compare serving patterns (batch / real-time / streaming) and reason about the latency–throughput tradeoff.
  • Explain inference optimization: quantization, pruning, distillation, compilation.
  • Distinguish data drift, concept drift, and data-quality failures; design monitoring for each.
  • Compare shadow, canary, and A/B deployments; diagnose production incidents from signals.

13.1 The lifecycle, CI/CD, and the registry

The ML lifecycle is a loop, not a line: data → features → training → validation → deployment → monitoring → (new data) → retraining. Everything in this topic exists because the loop never terminates — the world that generated your training data keeps moving after you ship.

Training–serving skew is the classic first failure: offline metrics are great, online behavior is bad, and the cause is that the serving path computes features differently from the training path. Typical culprits: a feature re-implemented in another language for latency; a "last 30 days" aggregate that quietly used future data during training (leakage — Topic 4); a library version bump that changes tokenization. The cures are structural, not heroic: share one feature-computation code path (a feature store — Topic 6), log the serving-time feature values and train on those logs, and pin every version.

CI/CD for models extends software CI/CD with two new test families. Alongside unit tests you add data tests (schema, ranges, null rates, distribution checks on every incoming batch) and model tests (quality on a golden holdout, slice metrics — Topic 7, behavioral invariance checks, latency budget). The load-bearing component is the validation gate: a candidate model is promoted only if it beats the incumbent on held-out and slice metrics, and never automatically otherwise — including candidates produced by automated retraining (on a schedule, or triggered by the drift monitors of §13.4). A pipeline that retrains automatically but promotes through a gate is "MLOps level 2" in Google's maturity model; a notebook and a prayer is level 0.

The model registry is the system of record: every model version with its lineage — training-data snapshot/hash, code commit, hyperparameters, metrics, and current stage (staging → production → archived). Lineage is what makes rollback trivial and audits possible ("which data trained the model that made this decision?" — a regulatory question, Topic 7 and Topic 20). Think of it as the lab notebook requirement: a result you cannot reproduce is not a result, and a model you cannot trace is not deployable.

13.2 Serving — patterns and the latency–throughput tradeoff

Three serving patterns, chosen by when predictions are needed:

  • Batch: score everything on a schedule (nightly churn scores, weekly recommendations), store results in a database, serve lookups. Cheapest, simplest, hardware fully utilized; predictions can be stale by up to one period.
  • Real-time (online): a request arrives, the model answers within a latency SLO (tens of ms typically). Needed when the input only exists at request time (a search query, a fraud check on this transaction). All the hard problems of this topic live here.
  • Streaming: predictions ride an event stream (Kafka et al.) — fresher than batch without request/response coupling; natural for pipelines of events (clickstreams, sensor feeds).

Real-time serving lives on one tension: GPUs are throughput machines that love big batches, but users wait one request at a time. Dynamic batching is the standard resolution — the server holds arriving requests for up to a few milliseconds, groups them, and runs one batched forward pass. Batch size raises throughput (the fixed kernel-launch and memory-movement overhead amortizes) and raises latency (requests wait for the batch, then for a longer forward). Every serving stack (Triton, TorchServe, vLLM) is tuned around this dial.

⚛ Physics bridge

A serving system near capacity is a system near a critical point. In queueing theory the wait scales like \(\rho/(1-\rho)\) where \(\rho\) = load/capacity — the same divergence you know from critical slowing down: susceptibility blowing up as the control parameter approaches the transition. The practical law: tail latency diverges long before utilization reaches 100%. Operators leave headroom (ρ ≈ 0.6–0.8) for exactly the reason you never run a magnet at its quench current. 13.3 Making inference cheap — quantization, pruning, distillation, compilation

Training optimizes for learning; serving optimizes for cost and latency. Four standard compressions, usually composed:

TechniqueWhat it doesTypical winCost / risk
QuantizationStore/compute weights (and maybe activations) in INT8/INT4 instead of FP162–4× memory & throughputAccuracy loss if done naively; outlier channels in LLMs need care
PruningRemove weights (unstructured) or whole neurons/heads (structured)Sparsity 50–90%; real speedup only if structured or hardware-sparseAccuracy cliff past a threshold; retraining usually required
DistillationTrain a small student to match a big teacher's output distribution (soft labels)Order-of-magnitude smaller model at modest quality lossA full training job; student inherits teacher's blind spots
CompilationFuse kernels, optimize the graph for target hardware (ONNX Runtime, TensorRT, torch.compile)1.5–3× latency, no accuracy changeEngineering time; operator-coverage gaps

Quantization has two grades: post-training quantization (PTQ) — take the trained model, measure activation ranges on a few hundred calibration examples, pick scale factors, done in minutes; and quantization-aware training (QAT) — simulate the rounding during fine-tuning so the weights learn to live with it. PTQ first; QAT when PTQ's accuracy drop is unacceptable. The mechanics rhyme with Topic 12's precision story: quantizing is choosing per-tensor (or per-channel) units so values fill the integer range — gain-staging again, now at 8 bits. Distillation's soft labels work because the teacher's full distribution ("this 7 looks 20% like a 1") carries more information per example than the hard label — the dark knowledge argument of Hinton et al.

13.4 Monitoring — drift, label lag, and the metrics pyramid

Production monitoring is layered, cheapest and fastest signals first: system metrics (latency, error rate, saturation — seconds to detect), data metrics (schema violations, null rates, per-feature distribution distance — minutes), model metrics (prediction and confidence distributions — hours), and business metrics (the thing you actually care about — often days, because of label lag: you learn whether the loan defaulted months after you scored it). The art is using the fast layers as proxies for the slow ones.

The drift taxonomy the exam expects — for input \(x\) and target \(y\):

  • Data (covariate) drift: \(P(x)\) changes, \(P(y\mid x)\) doesn't. New user demographics, a new device type. Detectable without labels by comparing feature distributions.
  • Concept drift: \(P(y \mid x)\) changes — the world's rule changed. Fraudsters adapt, consumer taste shifts. Invisible to input monitoring; only labeled outcomes reveal it, after the lag.
  • Data-quality failure: not drift at all — a pipeline broke (nulls, unit change, stuck sensor). The most common in practice, the most sudden, and the most fixable.

The workhorse distance is PSI (population stability index): bin the reference (training) distribution, bin the live window, and compute \(\sum_i (p_i - q_i)\ln(p_i/q_i)\) — a symmetrized KL divergence (Topic 2). Rules of thumb: < 0.1 stable, 0.1–0.25 watch, > 0.25 investigate. Alternatives: Kolmogorov–Smirnov per feature, classifier two-sample tests. Alert on per-feature PSI, not one global score — localization is half the diagnosis.

⚛ Physics bridge

This is detector calibration drift. The training distribution is your reference spectrum; PSI compares today's spectrum against it, channel by channel — and a pipeline break looks exactly like a dead channel: a spike concentrated in one bin, instantly recognizable. Concept drift is nastier: the detector reads perfectly but the physics changed — no internal check can catch it; you need ground truth, and ground truth arrives with the delay of offline reconstruction. That's label lag.

Things to try: (1) Covariate drift: PSI climbs as the feature distribution slides — the input monitor fires days before any label arrives. This is why unlabeled monitoring exists. (2) Concept drift: PSI stays flat forever — inputs never changed — while true accuracy has already fallen; your dashboard finds out one label-lag later. Slide the lag to 45 days and feel the exposure. (3) Pipeline break: PSI leaps in a day (one bin swallows the null-imputed values). Fast, loud, and the reason data tests run on every batch.

13.5 Progressive delivery — shadow, canary, A/B

Never swap 100% of traffic to a new model. The standard ladder:

  • Shadow (dark launch): the new model receives a copy of live traffic; its answers are logged and discarded. Zero user risk. Validates latency, error rate, and output distributions on real inputs — but can't measure anything requiring user reaction.
  • Canary: route a small slice (1–10%) of real users to the new model, watch guardrail metrics (errors, latency, complaint rate, prediction sanity), and auto-rollback on breach. Catches what shadow can't: real feedback, real load interactions.
  • A/B test: a controlled experiment (Topic 2's hypothesis testing, alive and billing you): randomize users into arms, run to a pre-registered sample size, compare the business metric. The only rung that answers "is the new model actually better for users?" — noisier and slower than offline eval, and the final word.

The three answer different questions — does it run (shadow), does it break anyone (canary), does it win (A/B) — and mature teams run all three in sequence. Rollback must be one command, which is what the registry's version pinning bought you.

13.6 Incident triage — reading the dashboard

The exam's favorite format for this topic: here are six signals, what broke? The method is correlation-and-elimination: what moved together, what stayed flat, and what changed at that timestamp (deploys are the prime suspect — check the deploy log first). Latency moving without error/drift points at infrastructure; quality moving without latency points at data or concept; everything moving at a timestamp points at a deploy. Practice below.

A metric a rollout must not damage (latency, errors, complaints) — monitored with auto-rollback during canary.

Self-check

1. A weekly automated retraining pipeline produces a candidate that scores worse than the production model on the golden holdout. A correctly designed system will:

c. Automation retrains; gates promote. A worse-than-incumbent candidate shipping automatically is the signature failure of "level 2 pipeline, level 0 governance." Repeated gate failures are themselves a signal — often upstream data drift.

2. A fraud model's precision decays over three months. Per-feature PSI: all < 0.08. Latency and error rates: flat. Most likely:

b. Flat PSI rules out (a) and (c) — those move input distributions. Adversarial domains are concept-drift machines: the opponents' whole job is changing P(y|x) while staying inside normal-looking P(x). Defense: short retraining cadence and fast label collection.

3. Product wants personalized "weekly picks" emails, sent Mondays, for 40M users. The right serving pattern:

d. Predictions are needed at a known time, inputs exist in advance, staleness of hours is irrelevant — the definition of a batch workload. Choosing real-time here burns 10–100× the cost for zero user benefit. Pattern-matching workload to serving mode is a straight exam points.

4. INT8 post-training quantization drops your model's accuracy 4 points — too much. Reasonable next steps, in order:

a. The escalation ladder: PTQ's failure is usually scale granularity (outlier channels — common in LLMs), fixed per-channel or by mixed-precision fallback for the worst layers; QAT is the heavier hammer. (c) increases the error; (b) and (d) are overreactions.
