NLP & Large Language Models

A language model is a probability distribution over the next token — nothing more. Everything that looks like intelligence emerges from making that one prediction extraordinarily well at extraordinary scale. This topic covers the full pipeline: how text becomes tokens, what pretraining actually optimizes, how base models get adapted, and how anyone can tell whether the result is any good.

Learning outcomes
  • Describe BPE, WordPiece, SentencePiece, Unigram tokenization and their tradeoffs.
  • Explain next-token prediction and its emergent consequences; compare encoder-only (BERT), decoder-only (GPT), encoder-decoder (T5); contrast contextual vs static embeddings.
  • Explain in-context learning and few-shot prompting; compare full fine-tuning, LoRA/QLoRA, adapters, prefix-tuning by cost and effect; describe instruction tuning.
  • Explain decoding strategies (greedy, beam, top-k, top-p, temperature); describe hallucination's mechanistic causes and mitigations.
  • Apply evaluation methods (perplexity, benchmarks, LLM-as-judge) and their limits; diagnose contamination and benchmark gaming.

9.1 Tokenization — the compromise everything else stands on

Models operate on integers, so text must be chopped into vocabulary units. Whole words fail (millions of words, and "unhappiness" shares nothing with "happy"); raw characters work but make sequences 4–5× longer — and attention is quadratic. The industry compromise is subwords: frequent words stay whole, rare words split into meaningful pieces.

BPE (Byte-Pair Encoding): start from characters (or bytes), count the most frequent adjacent pair, merge it into a new token, repeat for N merges. The merge list is the tokenizer. WordPiece (BERT) picks merges by likelihood gain rather than raw frequency. Unigram (used via SentencePiece) goes top-down: start with a huge candidate vocabulary and prune tokens whose removal least hurts corpus likelihood — SentencePiece also treats the input as raw bytes/text including spaces, so it needs no language-specific pre-splitting (crucial for Japanese, Chinese, code). GPT-class models use byte-level BPE: the base alphabet is 256 bytes, so any string is tokenizable — no unknown-token failures, ever.

Tokenization explains a family of famous LLM quirks: arithmetic is hard partly because "12345" may split as "123", "45"; spelling questions are hard because the model never sees characters; non-English text costs 2–4× more tokens (worse compression → shorter effective context and higher API bills — an equity issue as much as an engineering one).

9.2 Pretraining and the three architectures

The pretraining objective is stark: maximize \(\sum_t \log p_\theta(x_t \mid x_{<t})\) over trillions of tokens — cross-entropy on next-token prediction (Topic 2's MLE, at planetary scale). The emergent consequence: predicting the next token of everything humans write requires implicitly modeling grammar, facts, style, sentiment, code semantics, and some amount of reasoning — the loss function never mentions any of them. Skills appear as capabilities of compression: the better the model compresses text (lower perplexity), the more world-structure it has internalized. Whether specific abilities "emerge" suddenly at scale or improve smoothly under better metrics is an active debate (see resources), but the engineering fact stands: scale up, and qualitatively new behaviors become reliable.

Embeddings, static vs contextual. word2vec/GloVe give each word one vector regardless of context — "bank" is the same in "river bank" and "bank loan." Transformer hidden states are contextual: the vector for "bank" is computed fresh from its sentence, disambiguated by attention. Every modern embedding model (Topic 14) is a transformer encoder pooled into one vector per text.

9.3 Adapting a base model

In-context learning is the zero-gradient miracle: put examples in the prompt and the model infers the pattern at inference time — "few-shot prompting." The model isn't updated; the computation happens in its activations. For many tasks, 5 good examples in the prompt beat a fine-tune you'd have spent a week on. Always try prompting first (this becomes a Level III decision framework in Topic 17).

When you do need weights to change:

  • Full fine-tuning updates every parameter. Highest ceiling; costs training-run memory (Topic 12: ~16 bytes/param with Adam — 112 GB for a 7B model) and produces a full model copy per task.
  • LoRA: freeze the base weights; learn low-rank updates \(\Delta W = BA\) (rank r = 8–64) beside attention/FFN matrices — Topic 1's low-rank insight applied to fine-tuning. Trainable params drop ~100–1000×; the adapter is megabytes; you can serve many adapters over one base model. QLoRA: additionally hold the frozen base in 4-bit — a 70B fine-tune fits on one 48 GB GPU.
  • Adapters / prefix-tuning: small bottleneck layers inserted per block / learned virtual tokens prepended to the KV cache. Historically important; LoRA largely won on quality-per-parameter and zero inference latency (it merges into the weights).

Instruction tuning converts a raw text-completer into an assistant: supervised fine-tuning on (instruction → good response) pairs, thousands to millions of them, spanning formats and tasks. Data quality dominates data quantity (the LIMA result: 1k excellent examples can beat 50k mediocre ones). What instruction data can't teach well — judgment among many acceptable answers — is what preference optimization (RLHF/DPO) adds in Topics 11 and 17.

9.4 Decoding — how a distribution becomes text

Each step, the model emits a distribution over ~100k tokens. What you do with it changes everything: greedy (argmax) is deterministic and gets trapped in repetition loops; beam search keeps the B most probable prefixes — right for translation (one correct answer), catastrophically dull for open generation; temperature rescales logits \(z/T\) before softmax — the Boltzmann knob: T→0 greedy, T=1 the model's honest distribution, T>1 adventurous; top-k keeps only the k most probable tokens; top-p (nucleus) keeps the smallest set whose mass exceeds p — adaptive where top-k is rigid: 3 candidates when the model is sure, 300 when it isn't.

Hallucination — mechanism, not mystery. A language model is trained to produce plausible continuations, and plausibility is not truth. Mechanistic causes: (1) the objective rewards fluent guesses — there is no "I don't know" gradient signal in next-token prediction; (2) facts seen once during training are stored weakly — retrieval from weights is lossy interpolation; (3) sampling adds randomness by design; (4) instruction tuning teaches the form of confident answers, which the model produces even when content is absent (sycophancy's cousin); (5) exposure bias — one bad sampled token conditions everything after it. Mitigations, in rough order of leverage: ground answers in retrieved documents (RAG, Topic 14); train/tune for calibrated refusals; decode conservatively for factual tasks; verify claims with a second pass or external tools; and design the product so unverified output is labeled as such. No known mitigation reaches zero; Level III treats hallucination as a risk to be budgeted, not eliminated.

9.5 Evaluation — the hardest problem in the room

Perplexity \(= e^{\text{cross-entropy}}\) measures raw prediction quality — ideal for comparing base models on identical data, meaningless across different tokenizers (per-token loss depends on how big tokens are!) and uninformative about instruction-following. Benchmark suites (MMLU for knowledge, GSM8K/MATH for math, HumanEval for code, etc.) provide standardized scores — but public benchmarks leak into training data (contamination), and models can be tuned to the test's format rather than its substance (benchmark gaming). Contamination symptoms: implausibly high scores on old public sets, big drops on freshly-written variants of the same difficulty, verbatim regurgitation of test items. LLM-as-judge — a strong model grading another's outputs — scales human-like evaluation cheaply but carries biases you must control: position bias (prefers the first answer — randomize order), length bias (prefers longer), self-preference (prefers its own family's style), and rubric drift. The professional stack: automatic metrics for regression testing, LLM-judge with bias controls for breadth, small human evaluations for calibration, and — above all — an eval set built from your actual task, refreshed often enough that it can't be memorized.

Self-check

1. Model A (32k vocab) reports perplexity 8; Model B (128k vocab) reports 11 on the same raw text. Which conclusion is sound?

c. B's bigger tokens each carry more information, so higher per-token perplexity may still mean better compression per character. Normalize per byte/character to compare. A classic exam trap.

2. You need 50 lightly-customized variants of a 13B model (one per client's tone). The economical architecture:

b. Adapter-per-tenant over a shared base is the standard multi-tenant pattern — 50 fine-tunes' storage and serving cost collapse to one model plus megabytes. (Modern servers batch requests across different LoRAs.)

3. Your summarizer occasionally invents statistics. Which change attacks the mechanism most directly?

d. Numbers are exactly what parametric memory interpolates worst. Grounding + conservative decoding + claim checking targets the cause. (a) increases hallucination; (c) helps but doesn't fix the objective mismatch.

4. A new model beats every 2-year-old public benchmark yet underperforms rivals on your fresh in-house tasks. First hypothesis:

a. Public-high/private-low is contamination's signature. Fresh, task-specific, held-private evals are the only numbers you should let drive decisions.
