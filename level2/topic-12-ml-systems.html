ML Systems Design & Distributed Training

Large-model training is a constrained design problem: a run must fit in memory, finish within time and budget, and move tensors quickly enough that accelerators do useful work. This chapter builds one auditable estimate at a time. Every number states its dtype, sharding group, unit, schedule, and efficiency assumption, so a rough calculation remains useful without pretending to be a profiler.

Learning outcomes
  • Describe data, model, tensor, and pipeline parallelism and choose when each is needed.
  • Explain ZeRO/sharded optimizer states and Fully Sharded Data Parallel (FSDP).
  • Calculate memory for parameters, gradients, optimizer states, and activations.
  • Describe FP16, BF16, FP8, mixed precision, and loss scaling.
  • Explain gradient accumulation, activation checkpointing, and their trade-offs.
  • Describe all-reduce, all-gather, reduce-scatter, and interconnect constraints.
  • Design a training cluster from model size, dataset, time, memory, and budget constraints.

A disciplined sizing order

First make the run feasible: estimate persistent state, peak activations, temporary buffers, and reserve. Then make it fast: map communication to the topology, choose batch and schedule, and measure throughput. Finally make it affordable and reliable: include storage, checkpoint time, failures, queueing, and uncertainty. A capacity calculation cannot prove performance.

12.1 Where the memory goes — the 16 bytes/parameter rule

Purpose — budget peak live memory, not checkpoint file size

Training memory is the maximum set of bytes simultaneously live on one device. A checkpoint may contain only weights and optimizer state, while a training step additionally holds gradients, activations, communication buckets, kernels' workspaces, allocator reserve, and sometimes a temporarily gathered layer. An out-of-memory error is caused by that peak, not by the average or by the checkpoint size.

Start with a ledger. For \(N\) parameters and component byte widths \(b_p,b_g,b_o\), unsharded persistent state is $$ M_{\text{state}}=N(b_p+b_g+b_o). $$ The symbols must describe the actual implementation: gradient dtype, master-weight policy, optimizer, quantization, and offload all change the answer.

The byte ledger — when 16 bytes per parameter is valid

GradientsBF16 or FP16: 2 B/parameterSome reductions or gradient buffers use FP32: 4 B; buckets can add a temporary copy.
Master parametersFP32: 4 B/parameterOptional in some optimizer/framework recipes, mandatory in others.

Scaling warning

“The model is 14 GB” usually means 7 billion two-byte inference weights. Under the ledger above, training state is \(7\times10^9\times16=112\) GB, or about \(104.3\) GiB, before activations and reserve. Always attach the phase and dtype to a memory number.

Worked state calculation — a 7B model with ideal ZeRO sharding

Let parameters use 2 B, gradients 2 B, and optimizer/master state 12 B. Without sharding, each data-parallel rank holds \(14+14+84=112\) GB. Across an eight-rank ZeRO stage-3/FSDP shard group, the ideal persistent share is $$ \frac{14+14+84}{8}=14\text{ GB}=13.0\text{ GiB per rank}. $$ That does not mean a 16 GB device is safe: layer all-gathers, activations, temporary workspaces, communication buffers, fragmentation, and framework reserve still contribute to peak memory.

Activations and transients — the controllable, shape-dependent term

Activations generally grow with micro-batch \(b\), sequence length \(s\), hidden width \(h\), and depth \(L\). A useful first proxy is \(M_{\text{act}}\propto bshL\), but attention implementations that materialize score matrices can add terms proportional to \(bs^2L\). Memory-efficient exact attention avoids storing the full score matrix by tiling and recomputing; it does not make every other activation disappear.

Peak memory can also include the largest operator workspace, fused optimizer buffers, gradient buckets, gathered FSDP units, and allocator fragmentation. Measure allocated and reserved peak memory after warm-up at the intended shapes, then keep operational headroom.

Gradient accumulation — enlarge the update without enlarging one micro-batch

With fixed-size sequences, micro-batch \(b_\mu\) per rank, \(a\) accumulation steps, and \(d\) data-parallel ranks, $$ B_{\text{global}}=b_\mu a d,\qquad T_{\text{update}}=B_{\text{global}}s. $$ Accumulation holds only one micro-batch's activations at a time. It increases work and latency per optimizer update, and communication should normally be suppressed until the last micro-batch. 

zero gradients
for micro_step = 1 ... accumulation_steps:
    loss = forward(next_micro_batch)
    backward(loss / accumulation_steps)   # if losses are means
    do not synchronize gradients yet, except on the final micro-step
unscale gradients if mixed precision
clip gradients if required
synchronize, optimizer_step, update_schedule

This can approximate a larger batch, but is not automatically bit-for-bit or statistically identical. Batch-normalization statistics, dropout draws, loss reduction, variable token counts, gradient clipping, overflow handling, optimizer updates, and floating-point summation order can differ.

Activation checkpointing — save boundaries, replay interiors

Checkpointing deliberately discards selected forward intermediates. During backward, the system reruns the necessary forward region from a saved boundary. Fewer/larger segments usually store fewer boundaries but create more recomputation and may extend the live range of some tensors. The memory reduction and compute penalty are graph- and implementation-dependent; “33% extra compute” is a possible rough case, not a guarantee. 

for segment in model_segments:
    save(segment_input)
    run_forward_without_saving_interior(segment)
during backward:
    restore_saved_input
    replay_segment_forward_with_needed_intermediates
    differentiate_segment

⚛ Physics bridge

Checkpointing resembles storing sparse states of a simulation and re-integrating between them. The important quantity is the maximum simultaneous working set, just as an instrument must tolerate the peak signal rather than its time average.

12.2 Mixed precision — FP16, BF16, FP8 and loss scaling

Range and precision — exponent bits and significand bits do different jobs

Floating point is binary scientific notation. Exponent width controls dynamic range; significand precision controls relative rounding. Lower precision can reduce storage and use faster accelerator paths, but stable training normally keeps sensitive reductions, accumulations, or optimizer state in a wider format.

Format or modeMain ideaTraining interpretation
FP328 exponent, 23 stored fraction bitsWide range and finer precision; common for optimizer states and sensitive operations.
TF32FP32 storage/range with reduced multiply precision on supported matrix hardwareA matmul execution mode, not a two-byte storage dtype.
FP165 exponent, 10 fraction bits; max 65,504Narrow range; gradients may underflow and activations may overflow.
BF168 exponent, 7 fraction bitsFP32-like range with coarser rounding; often easier to train than FP16, not automatically stable.
FP8 familiesVariants trade exponent range for significand precisionUsually paired with tensor/channel/block scaling and higher-precision accumulation/state; exact limits depend on the FP8 format.

FP16's smallest positive normal is about \(6.10\times10^{-5}\), while its smallest positive subnormal is about \(5.96\times10^{-8}\). Subnormals provide a narrow gradual-underflow region, but some hardware paths may flush tiny values. Do not equate “below minimum normal” with “certainly zero.”

FP16 loss scaling — move gradients temporarily, then undo the move

If \(L'=SL\), differentiation gives \(\nabla L'=S\nabla L\). Backpropagate the scaled loss, then divide gradients by \(S\) before clipping and updating. With \(g=10^{-8}\) and \(S=2^{15}=32768\), the backward value is \(3.2768\times10^{-4}\), comfortably normal in FP16; unscaling recovers the intended magnitude subject to rounding. 

with lower_precision_forward:
    loss = model(batch)
scaled_loss = scale * loss
backward(scaled_loss)
unscale_gradients()
if every gradient is finite:
    clip_if_required()
    optimizer_step()
    perhaps increase scale after a stable interval
else:
    skip the update and reduce scale
zero_gradients()

Scaling the loss cannot repair overflow that already happened in the forward pass, a bad normalization, an unstable optimizer, or information lost when activations were rounded.

BF16, TF32, and FP8 — choose a recipe, not a slogan

  • BF16 preserves FP32-like exponent range, so loss scaling is often unnecessary, but coarse rounding, reductions, or particular models can still require care.
  • TF32 accelerates eligible FP32 matrix operations on supporting hardware while tensors can remain FP32. Its behavior and enablement are framework/hardware settings.
  • FP8 needs an explicit format and scaling policy. Forward activations, weights, and backward gradients may use different variants; scaling can be per tensor, channel, or block, with higher-precision accumulation and state.
  • Mixed precision means selective precision. Normalization, softmax, loss reduction, gradient accumulation, and optimizer math are common places to retain wider formats.

A stability workflow — measure before lowering another bit

  1. Establish an FP32 or trusted BF16 reference for loss, gradients, and task metrics.
  2. Enable autocasting with a documented allow/deny policy; retain sensitive operations in wider precision.
  3. For FP16, monitor dynamic-scale growth, skipped steps, infinities, and zeros after unscaling.
  4. Compare convergence and final metrics over multiple seeds, not only step throughput.
  5. Introduce FP8 one tensor family at a time; log amax/scales and saturation or underflow statistics.
  6. Choose the lowest-precision recipe that meets stability and quality requirements on the target hardware.

12.3 The parallelism menu — data, tensor, pipeline, ZeRO

The map — decide which axis of work or state to partition

MethodWhat is partitioned?Frequent communicationBest first reason to use it
Data parallel (DP)Input batch; model replicatedGradient all-reduce or reduce-scatterThe complete training state fits per rank and more throughput is needed.
ZeRO/FSDPOptimizer state, gradients, and optionally parameters across a DP groupReduce-scatter and all-gather around computationReplicated model state no longer fits efficiently.
Tensor parallel (TP)Operations/tensors inside a layerActivation collectives within layersA layer or its working set is too large, or large matmuls need more devices.
Pipeline parallel (PP)Groups of layers by depthPoint-to-point boundary activationsThe model is naturally stageable and can be balanced across devices/nodes.

“Model parallelism” is an umbrella term that includes tensor and pipeline partitioning; it is not a fifth mutually exclusive method. Sequence/context and expert parallelism partition other axes. A composed configuration usually satisfies $$ W=d_{\mathrm{DP}}d_{\mathrm{TP}}d_{\mathrm{PP}}, $$ with ZeRO/FSDP sharding applied over a specified data-parallel group, not automatically every GPU.

Data parallelism — replicated state, partitioned examples

Each replica runs forward and backward on different examples. Its local gradient is reduced so replicas apply a consistent update. Frameworks may sum and divide separately, so check whether the loss and collective produce a sum or mean. DP is simple and throughput-friendly when model state fits; adding DP ranks does not by itself reduce replicated state per rank.

ZeRO and FSDP — remove redundancy stage by stage

Idealized stageParametersGradientsOptimizer state
Replicated DP\(P\)\(G\)\(O\)
ZeRO-1\(P\)\(G\)\(O/d\)
ZeRO-2\(P\)\(G/d\)\(O/d\)
ZeRO-3 / fully sharded style\(P/d\)\(G/d\)\(O/d\)

These are steady-state shares under balanced ideal sharding across group size \(d\). A fully sharded implementation gathers parameter units just in time and reduce-scatters gradients, so peak memory includes the largest gathered unit and buffers. PyTorch FSDP and ZeRO-3 express a similar high-level sharding idea, but they are not interchangeable names for identical software, schedules, state-dict behavior, or performance.

Tensor parallelism — split each operation where links are fast

A matrix multiplication can be column- or row-partitioned so ranks compute slices, then exchange partial activations. The exchanges occur inside many layers and micro-batches, which makes latency and effective bandwidth important. TP is commonly placed on the fastest topology domain, but whether it may cross a node depends on model shapes, implementation, and the actual fabric—not a universal one-node rule.

TP also imposes divisibility and layout constraints: hidden size, attention heads, vocabulary, and expert counts may need to divide across ranks. Small local matrices can lose kernel efficiency before memory becomes the limit.

Pipeline parallelism — split depth and account for the schedule

Pipeline stages hold different layer ranges and pass boundary activations point to point. Balance matters: the slowest stage limits throughput. For the simple fill-then-drain schedule with \(p\) equal-time stages and \(m\) micro-batches, the ideal bubble fraction is $$ f_{\text{bubble}}=\frac{p-1}{m+p-1}. $$ At \(p=4,m=12\), \(f=3/15=20\%\). One-forward-one-backward, interleaving, asynchronous schedules, unequal stages, and communication produce different bubbles and memory behavior.

When to use what — start with the cheapest communication pattern

  • If full state and activations fit comfortably, start with DP; it is the simplest baseline.
  • If replicated state is the problem, shard within the DP group before splitting every layer.
  • If a layer or per-stage working set still cannot fit, add TP and/or PP, respecting topology.
  • If PP is underfilled, add micro-batches or use a better schedule—while checking activation memory and optimization batch size.
  • At every step, compare measured compute, communication, and idle time. More dimensions create more failure modes.

12.4 Communication — the primitives and the pipes

Collectives — name the output each rank receives

PrimitiveInput → output per rankTypical training role
All-reduceEach rank contributes \(M\); every rank receives the reduced \(M\)Combine replicated-DP gradients. Averaging may be a separate division.
Reduce-scatterReduce contributions, then each rank receives one shardLeave gradients or optimizer results sharded.
All-gatherEach rank contributes one shard; every rank receives their concatenationMaterialize sharded parameters or activations. It does not reduce values.
BroadcastOne source value becomes available to all ranksDistribute initialization or metadata.
Point-to-point send/receiveOne rank transfers to anotherPipeline boundary activations and gradients.
All-to-allEvery rank sends a distinct shard to every other rankRoute tokens among mixture-of-experts ranks.

For an ideal ring with \(n\) ranks and full logical tensor size \(M\), the per-rank payload is $$ V_{\text{gather}}=V_{\text{reduce-scatter}}=\frac{n-1}{n}M,\qquad V_{\text{all-reduce}}=2\frac{n-1}{n}M. $$ This is algorithm-level payload, not guaranteed wire traffic or elapsed time.

The \(\alpha\)-\(\beta\) model — separate latency from payload time

A useful approximation is \(T\approx k\alpha+V/B_{\mathrm{eff}}\): \(k\) sequential message steps, startup latency \(\alpha\), transferred payload \(V\), and measured effective bandwidth \(B_{\mathrm{eff}}\). For ring all-reduce, \(k=2(n-1)\). With \(n=8\) and \(M=4\) GiB, each rank moves \(7\) GiB. At an illustrative effective \(50\) GB/s, payload time alone is about \(7\times2^{30}/(50\times10^9)=0.150\) s; latency and contention add to it.

Topology and overlap — bandwidth labels are not application throughput

Device links, switches, network interfaces, and cross-rack paths form a hierarchy. Quoted per-link, per-direction, aggregate, line-rate, and payload bandwidth are different quantities. Collective performance also depends on message size, topology mapping, concurrent jobs, protocol overhead, and stragglers. Benchmark the actual collective sizes and groups.

SymptomLikely mechanismInvestigation
Many tiny collectivesLatency/startup dominatesBucket safely, fuse operations, or change partition granularity.
Large exposed collectiveBandwidth or topology dominatesOverlap with backward, use reduce-scatter, map groups locally, inspect contention.
One rank delays everyoneInput, thermal, kernel, or network stragglerCompare rank timelines and tail latency, not only average bandwidth.
Scaling flattensLocal work shrinks while communication/idle time remainsMeasure strong-scaling efficiency and stop adding ranks when time saved is not worth cost.
Fast microbenchmark, slow trainingDifferent sizes, groups, overlap, or contentionProfile the real step and reproduce its concurrency.

Communication can be hidden only behind independent useful work. “Overlapped” is therefore a timeline claim to verify, not permission to subtract all communication from the budget.

⚛ Physics bridge

Distributed training has a surface-to-volume problem. Useful matrix work grows with each partition's volume, while exchanged boundaries and synchronization behave like a surface term. Strong scaling eventually loses because the local volume shrinks but startup and boundaries do not vanish.

12.5 Sizing a run — FLOPs, GPU-hours, dollars

Roofline and utilization — distinguish an upper bound from a forecast

Operational intensity \(I\) is useful operations per byte transferred at a stated memory level. The basic Roofline bound is $$ P_{\text{attainable}}\leq\min(P_{\text{peak}},B_{\text{memory}}I). $$ If peak is \(1000\) TFLOP/s, bandwidth is \(3\) TB/s, and \(I=200\) FLOP/B, the bandwidth ceiling is \(600\) TFLOP/s, so this simplified kernel is bandwidth-bound. Roofline is a bound: kernels, dependencies, communication, launch gaps, and input stalls can make achieved performance lower.

Model FLOPs utilization is $$ \mathrm{MFU}=\frac{\text{useful model FLOPs}} {\text{advertised peak FLOPs}\times\text{elapsed seconds}}. $$ State the useful-FLOPs convention and precision peak. Activation recomputation raises actual hardware work without necessarily raising the numerator, so a busy accelerator need not have high MFU.

Run sizing — tokens, steps, wall time, GPU-hours, and cost

For a dense decoder-only transformer, \(C\approx6ND\) is a common first-order training heuristic: \(N\) non-embedding-like parameters and \(D\) training tokens. Architecture, attention length, embeddings, sparsity/MoE, recomputation, and implementation can require a model-specific FLOP count. Given achieved useful throughput \(q\) per GPU and \(g\) GPUs, $$ t=\frac{C}{gq},\qquad H_{\mathrm{GPU}}=\frac{gt}{3600},\qquad \text{compute cost}=H_{\mathrm{GPU}}\times\text{price per GPU-hour}. $$

Worked estimate: \(N=7\times10^9\), \(D=1.4\times10^{12}\) gives \(C=5.88\times10^{22}\) model FLOPs. With 256 GPUs, a stated 990 TFLOP/s peak, and 40% MFU, \(q=396\) TFLOP/s, so idealized wall time is about 161.1 hours (6.71 days), total 41,247 GPU-hours, and $103,000 at $2.50/GPU-hour. This excludes non-compute charges, failures, evaluation, checkpointing, and queue time.

Design the cluster — satisfy feasibility, time, topology, and reliability together

QuestionEvidence requiredCommon failure if omitted
Does one rank fit?Assumption-explicit ledger plus profiled peak and reserveOOM during a larger shape, gather, evaluation, or checkpoint.
Do group sizes divide cleanly?World-size equation and model-dimension divisibilityInvalid layout or padded, inefficient kernels.
Can the fabric carry the collectives?Representative size/group benchmarks and rank topologyAccelerators wait while scaling efficiency collapses.
Will the batch optimize well?Global non-padding tokens, schedule, convergence studyA fast system takes fewer but worse optimization steps.
Can the run recover?Checkpoint duration, durable storage, restart rehearsal, spare capacityA single fault erases days or makes the deadline impossible.

Use the smallest cluster that meets the deadline with acceptable risk, not automatically the largest cluster available. Strong-scaling efficiency, queue constraints, fault rate, and checkpoint overhead can make more GPUs cost more without proportionally reducing completion time.

Self-check

1. Under the stated recipe—2-byte parameters, 2-byte gradients, 4-byte master parameters, and two 4-byte Adam moments—how much persistent state does a 7B model require before sharding?

c. The ledger is \(2+2+4+8=16\) B/parameter, so \(7\times10^9\times16=112\) GB, about 104.3 GiB. The answer depends on the recipe.

2. An eight-rank ideal ZeRO-2 group has component sizes \(P=14\) GB, \(G=14\) GB, and \(O=84\) GB. What steady-state share does each rank hold?

b. ZeRO-2 replicates parameters but shards gradients and optimizer state: \(14+14/8+84/8=26.25\) GB. Buffers and activations are additional.

3. Micro-batch 2, accumulation 8, and 16 data-parallel ranks use full 2,048-token sequences. What contributes to one optimizer update?

d. Global sequences are \(2\times8\times16=256\), then \(256\times2048=524{,}288\) tokens. With padding, count real non-padding tokens instead.

4. Which statement about mixed precision is most precise?

a. Loss scaling affects the backward gradient path. FP16 has subnormals; BF16 trades precision for range; TF32 is a matmul mode; FP8 recipes and scales vary.

5. Which mapping best matches the communication pattern to the method?

c. Those patterns explain the topology choices. Exact collective schedules depend on the implementation.

6. A simple fill-drain pipeline has 4 equal stages and 12 micro-batches. What is its ideal bubble fraction under the chapter's stated formula?

b. \((p-1)/(m+p-1)=3/15=0.20\). Other schedules and imbalance change the result.

7. For an ideal ring all-reduce over 8 ranks with logical tensor size 4 GiB, what is the per-rank algorithmic payload?

d. \(2(n-1)M/n=2(7/8)(4)=7\) GiB. Protocol, topology, and contention still affect wire traffic and time.

8. A kernel has peak 1,000 TFLOP/s, memory bandwidth 3 TB/s, and operational intensity 200 FLOP/B. What does the basic Roofline model say?

a. \(\min(1000,3\times200)=600\) TFLOP/s. Roofline is an upper bound, not a throughput guarantee.

9. Using \(C=6ND\), what is the model-FLOP estimate for 7B parameters trained on 1.4T tokens?

c. \(6(7\times10^9)(1.4\times10^{12})=5.88\times10^{22}\). It is a dense-transformer heuristic, not a profiler replacement.

10. A proposed layout fits the ideal sharded state but leaves 0.5 GiB free and was not tested at the longest sequence. What is the sound cluster-design conclusion?

b. A design must satisfy peak memory, topology, performance, optimization, budget, and recovery constraints together. Ideal persistent shares are only one input.
